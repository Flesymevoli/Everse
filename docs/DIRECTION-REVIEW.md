# YunoTavern 工程审查与增量计划

日期：2026-11-09。审查基线：`2851655ed7dc608a8e617c86199b29a716ce0474`。本轮只读业务代码、编写规划，没有改数据库、安装依赖或调用模型。

**方向：Agent 驱动的开放式互动小说；SillyTavern 是兼容来源，不是产品结构。** 保留 React、Hono、SQLite 和文本生成接口。Agent 的价值应体现为维护可检查的故事事实、安排必要的工作与恢复失败，而非增加固定的多模型调用链。

## 按依赖排序的开发计划（尚未实现）

### P0：一个“能记住状态”的最小故事闭环

1. **统一作品入口和来源记录。** 先支持一句话、粘贴文本、TXT/Markdown，并复用现有 ST 导入适配器。保存原文/原始文件、来源、解析版本与未支持项；运行视图按需生成，原资料不覆写。新增作品定义不要求作者人物卡；旧存档继续按原资源 ID 读取，不全库转换。
2. **动态开局。** 有作者开场/玩家设置就优先呈现；无开场时一次生成开场及初始状态，可直接接受默认身份。只针对阻碍开局的矛盾询问，最多少量可跳过问题，不做每步模型问卷。作者规则不能被基础引导悄悄覆盖。
3. **最小叙事状态。** 当前场景/时间、出场人物、目标、已发生事实和未解决事件；不预设通用战斗数值或背包体系。普通回合优先同一次文本生成返回正文与有边界的结构化增量，不要求 Tool Calling。程序校验类型、实体引用、来源回合和基准版本，再提交；模型输出不能变成任意数据库/文件指令。
4. **一致性先行。** 每次成功回合同事务保存正文、状态增量和事实记录；玩家可查看、纠正、撤销纠正，下一轮使用修正值，不要求玩家审核每一轮。分支和候选关联各自状态；编辑旧文后相关派生记忆失效。已有存档默认状态为空、未初始化，不后台付费重建。
5. **失败可恢复。** 生成草稿与已提交剧情分开；结构化结果无效时保留正文草稿、维持旧状态并提示尚未同步，不把失败增量当成成功。支持重试/继续，禁止自动多次付费修复。加入任务 ID、基准版本和幂等提交，防止断线后的双写。

**可试玩验收：** 输入“雨城侦探”即可生成开场，连续游玩至少 10 轮；NPC 目标、已获得线索和当前位置能显示并参与下一轮；玩家修正一条事实后持续生效；重启、重写和切换分支不串状态。至少一个中断和非法增量样例不破坏旧存档。目标是正常每轮一次模型请求；若文本协议稳定性不足，先记录失败率和额外成本，不默认增加多个 Agent 补救。

**为什么先做它：** 同时解决“从零开局”和“世界确实被维护”两项产品核心，复用现有阅读/模型/保存链路；比先增加 Persona、群聊或完整作者工具，更早验证引擎是否比普通聊天有价值。

### P1：统一文档输入与可验证的长期记忆

- 在同一导入入口加入 `.docx`，提取段落、标题、表格文本并保留源文件与段落位置；旧 `.doc`、扫描件、图片中的文本明确标为暂不支持，不静默丢失。不执行宏或外链，不要求用户转换成角色卡。
- 原始资料 / 运行事实 / 阶段摘要分离；先用程序化实体和关键词检索相关原文，再考虑全文索引，不先引入向量服务。长文只导入、分段和建立索引，不默认整篇发送给模型。
- 超过可配置阈值或章节结束才整理已提交回合；摘要标注覆盖范围、来源和版本，保留近期原文。整理期间单写者，失败不丢原文、不移动记忆版本；回合、分支和用户修正决定有效记忆。
- 从 P0 就记录调用用途、模型、已报告输入/输出/缓存用量、耗时和失败。供应商不报告用量时标未知，不把字节估算当账单。
- 在相同模型、初始资料、采样/输出条件和玩家行动脚本下，对照直接聊天、当前裁剪方案与新方案；跑 30–50 轮，检查事实矛盾、线索召回、NPC 目标连续性、用户修正保持，以及包含整理/失败调用的累计成本。分开比较完整历史与受同预算约束的聊天基线；未测出优势就调整方案，不宣称必然省 Token。

### P2：有限自主发展

基于已验证状态加入回合/场景时间驱动的 NPC 目标与待办事件。程序判断何时需要推进；尽量并入下一次正文生成，只在确有必要时单独调用，并受用户费用预算约束。让玩家看到行动后果并可干预，不要求玩家安排每个 NPC。没有游玩时默认不循环消耗 Token。

暂不做多 Agent 编队、Skill 市场、实时后台世界、异步多人、完整 RPG 数值系统或酒馆全功能复刻。

## 决策

### 用户补充的上下文方向（2026-11-09，以下尚未实现）

当前长文修复仅是完整存储和基础检索，不作为最终导入理解方案。下一步优先做**可修正的语义导入计划**：区分核心规则、世界资料、开局引导、叙事要求、条件机制和示例；每项保留原文范围，允许改分类及优先级。作者示例不自动成为已发生事件。关键规则可用紧凑约束保持连续性，条件规则按情境调取；“重要”不等于每轮发送全部原文。

解析按源文档版本执行并缓存，可取消和续做，先说明用量预算，不每轮重新分析整部作品。长文需要分批处理，但机械分段只是处理边界，最终分类应基于语义且保留跨段关联；错误、不确定及冲突应可见，不能靠第一次模型分类就永久定论。

其后再扩展事件记忆：事件、相关人物、来源、前后状态、目标、因果关联、未解决线索和再触发条件。明确区分已发生、人物意图和模型推断；因果关系未经依据不能当作事实。只为有影响的剧情追加增量，不每轮重写不断变长的摘要。阶段摘要可以辅助回顾，不能取代事件依据与原文。用故事回放分别评测事实召回、错误因果、用户纠正保持、额外调用与累计用量，再判断是否引入更多后台工作。

建议下一阶段只交付 P0，不换技术栈、不整体替换 Narrative Runtime。先把“原文—事实—状态—回合提交”连成可信闭环，再添加文档解析与按需记忆整理。是否长期更稳、更便宜，作为验收问题回答，而不是作为架构命名得出的结论。
